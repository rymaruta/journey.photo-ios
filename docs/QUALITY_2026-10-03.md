### 確かめて問題が無かったもの（主なもの）

- **401**: トークンを取り直して1回だけ送り直す。同時の 401 は取り直しを1本にまとめる。取り直せなければログアウト、圏外ではログアウトしない（`AuthRetryTests`）
- **ログアウトの後片付け**: いいね・保存・ブロック・下書き・見たストーリー・限定写真の一覧・通知の宛先は人ごとに切り替え・捨てている（URLCache だけが抜けていた → 直した）
- **投稿の二重送信・やり直し**: 二度押しは止まる。やり直しは前回の鍵で保存し直す（`UploadDoubleSubmitTests` ほか）
- **EXIF・GPS**: 無編集・編集・サムネのどの道も同じ関所で消して読み直して確かめる（`ImagePreparer.assertStripped`）。**実際の焼き込みは Linux では試せず、実機・macOS の CI で見る**
- **いいねの連打・数のずれ**: 送っている印で逆向きの同時送信は起きない。数はサーバーの答えを使う
- **Privacy Manifest**: 理由の申告が要る API のうちアプリが使うのは `UserDefaults` だけで、`CA92.1` で申告済み。依存ライブラリ側の申告は確かめていない
- **UI テストは本番を書き換えない**: 鍵を持たず、公開の GET だけを読む（書き込む口は 401）

## 障害が起きたとき（戻し方）

- **アプリ（TestFlight）**: 問題のビルドは App Store Connect の TestFlight で「テストを停止」にし、
  前のビルドを配り直す（ビルドは消えない）。直しは新しい版で出す——**同じ版を上げ直さない**
- **App Store 公開後**: ストアの版は戻せない。次の版を早期審査（Expedited Review）で出す。
  サーバー側で止められる機能（新しい口）は、サーバーを前の版に戻すのが早い
- **サーバー（photo-gallery）**: Web の手順に従う（このリポジトリでは扱わない）。アプリは
  道が無い 404 を古いサーバーとして扱う作りなので、新しい口を戻してもアプリは落ちない
- **個人情報の漏れが疑われるとき**: まず口を止める（サーバー）。そのうえで影響範囲（期間・
  写真の ID）を Web のログから洗う
