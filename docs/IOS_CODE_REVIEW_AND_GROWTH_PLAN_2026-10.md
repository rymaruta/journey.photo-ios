# Journey Photo iOS ソースレビュー・成長改善計画

- 作成日: 2026-10-21
- 対象リポジトリ: https://github.com/rymaruta/journey.photo-ios
- 関連Web: https://journey-photo.com
- 関連Webリポジトリ: https://github.com/rymaruta/photo-gallery
- 目的: リリース品質のリスクを明確にし、初回体験と認知獲得を改善するための実行可能な計画を定める

> この文書は、現時点で確認できたリポジトリ内の README、project.yml、Tools/verify.sh、docs/APP_STORE_METADATA.md、および直近のマージ済みPR情報に基づくレビューである。全Swiftファイルを一行ずつ監査した結果ではなく、実機での操作テストも実施していない。未検証事項は「要確認」として分離し、確認済みの事実と推測を混同しない。

## 1. 結論

Journey Photoには、撮影スポット検索、光の時刻、地図、旅の計画、写真投稿・交流をつなぐ独自の方向性がある。一方で、**機能の多さが、初めて見た人に伝えるべき価値を隠してしまうリスク**がある。

最優先は新機能をさらに増やすことではなく、次の3点を順番に確かめること。

1. **iPhone上で安定して使えること**を、iOS SDKを使ったビルド・シミュレータ・実機で確認する。
2. 初回起動から「撮りたい場所を見つける」「写真を見る」「行きたい場所を保存する」までを迷わず進めるようにする。
3. App Storeの検索結果・掲載画像・SNS投稿を同じ約束に揃え、認知から初回利用までの数字を測る。

### 暫定評価

| 領域 | 現時点の評価 | 根拠・注意 |
|---|---|---|
| コンセプト | 強みがある | 写真と撮影地、次の旅を結ぶ方向性は明確 |
| 機能の幅 | 広い | スポット検索・撮影準備・旅の記録・SNS機能を含む |
| 自動検査 | 工夫されている | Linux上のSwift検査、参照・設定・API整合性チェックがある |
| iOS本来の検証 | 未確認リスク | READMEとverify.shは、LinuxのShims検査が本物のSwiftUI実行を保証しないと明記 |
| 初見での価値伝達 | 要改善 | App Store掲載情報の設計文書が、公開中の1枚目画像では撮影スポットが伝わりにくいと指摘 |
| 新規ユーザー獲得 | 最優先課題 | 機能追加だけでは認知・インストール・継続利用は増えない |

## 2. 確認できた技術面の事実

### 2.1 ビルド・テストの意味を分ける

READMEおよび `Tools/verify.sh` では、Linux上でSwiftUI等のAPI形状を模した `Shims/` を使って構文・型・参照・テストを検査する仕組みが説明されている。また、iOS SDKを使った本物のビルドとシミュレータテストはMac上で行う必要があると明記されている。

これは有益な静的検査だが、**Linux側の検査成功を、実機で正常に動作する証拠として扱ってはいけない**。

推奨するリリースゲート:

- [ ] `bash Tools/verify.sh` が成功する
- [ ] Mac上で `xcodegen generate` が成功する
- [ ] Mac上で `xcodebuild build test` が成功する
- [ ] TestFlightビルドを実機にインストールし、主要フローを確認する
- [ ] 本番API・staging APIの接続先と設定値を確認する
- [ ] リリースしたビルド番号とApp Store Connect上のビルド番号が一致する

### 2.2 プロジェクト構成

確認した `project.yml` では、XcodeGenでプロジェクトを生成し、iOS 17以降を対象とするSwiftUIアプリとして定義されている。AWS Amplifyの認証関連パッケージを利用し、DebugとReleaseで別のxcconfigを使う構成である。

この構成自体は運用可能だが、環境切り替えは事故が起きやすい領域である。特に、stagingのデータを本番として扱う・本番ユーザーにstagingの認証設定を使う、といった誤設定がないかをリリース前に確認する。

### 2.3 API整合性の検査

`Tools/verify.sh` はWeb版の `api-user` とのAPI整合性チェックを実行する構成になっている。これはiOSとWebの契約ずれを早めに見つけるために有用。

ただし、静的な整合性チェックだけでは、実際の通信失敗、タイムアウト、画像アップロードの途中失敗、認証切れ後の再試行、サーバー側データの欠落など、実行時のユーザー体験までは保証できない。

### 2.4 直近の開発傾向

直近のマージ済みPRには、キャンパー内装・家具メッシュ、パネル調整、写真フレーム表示などの作業が含まれている。PR説明上はテスト成功の記載がある一方、実機での見た目や操作感は未検証とされているものがある。

これは不具合の証拠ではない。ただし、**目に見える機能を増やす開発と、アプリの中核価値・安定性・新規ユーザー獲得を改善する開発の配分**は定期的に見直したい。

## 3. 優先度別の技術レビュー計画

以下は現時点で確定したバグ一覧ではなく、実際の画面・通信・実機を監査して判定すべき項目である。

### P0 — リリース前に必ず確認

#### A. 起動・環境設定
- [ ] 初回インストール直後にクラッシュせず起動する
- [ ] 未ログインでも、説明されている閲覧機能が使える
- [ ] ログイン・ログアウト・認証期限切れ後の挙動が破綻しない
- [ ] Debugはstaging、Releaseは本番を参照する
- [ ] API URL、Cognito設定、Bundle ID、版番号が各環境で一致する
- [ ] ネットワークが遅い／切れている場合に、無限ローディングにならず再試行できる

#### B. 写真の投稿・表示
- [ ] 写真選択から投稿完了まで、進行状態と失敗理由が分かる
- [ ] アップロード中にアプリを閉じた場合の状態が明確
- [ ] 大きい画像、縦長・横長画像、複数画像を扱える
- [ ] サムネイルと詳細表示で画像が入れ替わらない
- [ ] 画像読み込み失敗時にプレースホルダーと再試行が表示される
- [ ] 連続スクロール時にメモリ使用量や読み込み待ちが悪化しない
- [ ] EXIF/GPSの取り扱いと画面上の撮影情報が、プライバシー説明と一致する

#### C. 認証・プライバシー・UGC
- [ ] 未ログインで許可される操作と、ログインが必要な操作が一貫している
- [ ] 通報・ブロック・アカウント削除がアプリ内から完了できる
- [ ] ブロックした相手の投稿・コメント等が仕様どおりに非表示になる
- [ ] 写真の位置情報が説明どおりに処理される
- [ ] カメラ・写真・位置情報などの権限を拒否した場合にも、アプリが利用不能にならない
- [ ] Bluetoothや位置情報に関する機能は、許可の目的と停止方法が理解できる

### P1 — 初回体験と継続利用に直結

#### D. ホーム・検索・スポット詳細
- [ ] 初回起動から数秒で、アプリの価値と次に押す場所が分かる
- [ ] 検索結果0件、通信失敗、画像なし、データ未取得の状態がそれぞれ説明される
- [ ] 検索条件の追加・解除が分かりやすい
- [ ] スポット詳細から「保存」「地図」「経路」「関連写真」に迷わず移動できる
- [ ] 地図のピンをタップした時と、リスト項目をタップした時の対象が一致する
- [ ] 季節・時間帯のおすすめが古いデータや空データでも不自然にならない

#### E. フィード・プロフィール・交流
- [ ] いいねの連打・取り消し・通信失敗時に表示がサーバー状態とずれない
- [ ] フィードをスクロールして戻ったとき、位置や表示状態が過度にリセットされない
- [ ] プロフィール編集で保存中・成功・失敗が区別できる
- [ ] フォロー・コメント・保存などの操作に一貫したフィードバックがある
- [ ] 通知が届かないケースを、通知設定・権限・サーバー側状態に分けて診断できる

### P2 — 品質と運用の改善
- [ ] 主要画面の表示速度、画像読み込み時間、クラッシュ率を計測する
- [ ] エラーに画面名・処理名・環境を付け、個人情報や画像データは記録しない
- [ ] APIのページネーション・重複取得・キャッシュ無効化を確認する
- [ ] アクセシビリティ、文字サイズ、VoiceOver、ダークモード、通信不安定時を確認する
- [ ] UIテストは、画面の存在だけでなく主要な操作結果を検証する

### テストの最低シナリオ

1. 未ログインで起動 → スポット検索 → 詳細 → 地図 → 保存を試す（保存に認証が必要なら、その案内を確認）。
2. アカウント作成 → 写真1枚を投稿 → 詳細表示 → いいね → 取り消し。
3. 写真ライブラリ権限を「選択した写真のみ」にして、写真を選択・追加できるか確認。
4. 通信を切断して検索・投稿を試し、失敗表示と復旧後の再試行を確認。
5. ログアウト → 再ログインし、プロフィール・投稿・保存が期待どおりか確認。
6. 通報・ブロック・アカウント削除までの導線を確認。
7. TestFlightの本番相当設定で、別アカウント・新規インストールでも同じ結果になるか確認。

## 4. 認知されない原因の仮説

「認知が少ない」ことだけでは、原因がApp Store検索なのか、掲載ページからのインストール率なのか、インストール後の離脱なのかは特定できない。まず、次の3つを分けて考える。

1. **見つけてもらえない** — 検索順位、SNSでの露出、外部リンクが足りない。
2. **見つけてもインストールされない** — アイコン・タイトル・最初のスクリーンショット・説明が魅力を伝えていない。
3. **インストール後に定着しない** — 初回体験、写真やスポットの量、投稿する動機、コミュニティの活動量が不足している。

### 4.1 App Store掲載の課題

`docs/APP_STORE_METADATA.md` は、2026-10-07時点の掲載画像の1枚目が「フランスとラーメン」の写真で、撮影スポットアプリであることが伝わりにくいと記録している。また、App Storeの「撮影スポット」検索ではJourney Photoが上位8件に表示されなかったという記録がある（当時の検索結果に限る。現在の順位は再確認が必要）。

現在の掲載案は「Journey Photo 撮影スポット図鑑」で、撮影スポット検索を入口にしている。一方、ブランドの目標は「写真から、次の旅が始まる」写真SNSである。これは必ずしも矛盾ではないが、初見ユーザーにとって、**撮影地ガイドなのか、写真SNSなのか、旅の記録アプリなのか**が曖昧にならないよう、主役を一つに決めて表現を統一したい。

### 4.2 推奨するブランドメッセージ

**ブランドの中心:**
> 写真から、次の旅が始まる。

**初めての人向けの説明:**
> みんなの写真から、次に行きたい場所を見つけよう。撮影スポットを探して、旅を計画して、自分の写真も残せるアプリ。

**投稿募集の呼びかけ:**
> 写真好きのための場所を、一緒に育ててくれる人を募集中。使ってみた感想や「こうなったら嬉しい」という要望も、ぜひ教えてください。

SNSでは毎回すべての機能を説明せず、「写真を見ると行きたい場所が見つかる」という一つの体験を繰り返し伝える。

### 4.3 App Storeスクリーンショットの推奨順

最初の3枚だけでもアプリの魅力が分かる構成にする。

1. **日本の撮影スポット詳細** — 「日本中の『撮りたい』が、ここに。」
2. **日の出・ゴールデンアワーなどの時刻** — 「いちばん美しい時刻がわかる」
3. **季節・見頃のスポット** — 「次の休日に撮りたい場所を見つけよう」
4. 地図 — 「旅先の近くの撮影地を地図で」
5. 行きたい場所・旅の計画 — 「保存して、そのまま旅の計画に」
6. 写真投稿・旅の記録 — 「撮った旅を、自分の記録に」

掲載画像には実際のアプリ画面を使い、利用できない機能や根拠のない件数・人気表示を載せない。スクリーンショット変更時は、現在の公開画面と文言を照合してから提出する。

## 5. 30日間の認知獲得プラン

広告費をかけず、個人開発者が継続できる量を前提にする。

### Week 1 — 入口を整える
- [ ] App Storeの現行タイトル、サブタイトル、キーワード、スクリーンショットを再確認
- [ ] 最初の3枚を撮影スポット・光の時刻・季節の価値に揃える
- [ ] WebサイトとApp Storeの説明・リンク・問い合わせ先を確認
- [ ] アプリ内で最初に試すべき行動を一つに絞る（例: スポットを見る → 保存する）
- [ ] 計測可能な範囲で、掲載ページ閲覧・初回起動・初回主要行動の基準値を記録

### Week 2 — 写真を入口に発信
週3〜4投稿を目安に、1投稿1テーマで発信する。

- 撮影スポットの作例写真 + 場所 + 撮影のポイント
- 日の出・夕焼けなど、撮りに行く時間を選ぶヒント
- 季節の撮影スポットを探す短い紹介
- Journey Photoの開発裏話と、改善した内容
- 写真好きに向けたフィードバック募集

投稿は宣伝だけにしない。役に立つ写真・撮影情報を先に届け、プロフィールや固定投稿からアプリへ誘導する。写真の利用権・出典・撮影者の許可を確認する。

### Week 3 — 小さな利用者グループを作る
- [ ] 写真好き・旅行好きに、まず5〜10人のテスターとして使ってもらう
- [ ] 「何が分かりにくかったか」「どこで止まったか」「何を保存したくなったか」を聞く
- [ ] 要望をそのまま全部実装するのではなく、複数人から出た課題を優先する
- [ ] 改善したら、変更内容と協力への感謝を発信する

### Week 4 — 数字で次の一手を決める
- [ ] 反応が多かった投稿テーマを特定する
- [ ] ストア閲覧があるのにインストールが少ないなら、掲載ページを改善する
- [ ] インストールはあるのに初回行動が少ないなら、オンボーディングを改善する
- [ ] 初回利用はあるのに再訪がないなら、保存・見頃・旅の計画など再訪理由を改善する
- [ ] 次の30日で改善する項目を最大3つに絞る

## 6. 最低限追いたい指標

最初から大量の分析基盤を作る必要はない。まずは、取得できるデータを確認し、取れない指標を取れると偽らないこと。

| 段階 | 指標 | 分かること |
|---|---|---|
| 認知 | SNS表示数・プロフィール遷移・リンククリック | 投稿が見られ、興味を持たれたか |
| ストア | App Store Connectの製品ページ閲覧・獲得数 | ページに来た人がインストールしたか |
| 初回利用 | 初回起動後にスポット詳細を開いた割合 | 最初の価値に到達できたか |
| 価値体験 | スポット保存・写真閲覧・投稿の実行数 | どの機能が使われたか |
| 定着 | 7日後・28日後の再訪 | また使う理由があるか |
| 安定性 | クラッシュ、主要API失敗、画像読み込み失敗 | 品質が利用を妨げていないか |

イベント計測を追加する場合は、撮影画像・正確な位置・メールアドレスなどを分析イベントに含めない。必要なイベント名・保存期間・利用目的を決め、プライバシー表示とも整合させる。

## 7. 実行順序と完了条件

### 最初に実施する5項目

1. [ ] Mac/Xcodeでの本物のビルド・テスト結果を記録する。
2. [ ] TestFlightで「未ログイン閲覧 → スポット詳細 → 写真表示 → 保存」の導線を確認する。
3. [ ] 写真投稿・認証・プライバシーのP0チェックを実機で行う。
4. [ ] App Storeの最初の3枚を撮影スポットの価値が伝わる構成に変更する。
5. [ ] SNS投稿を週3〜4本、30日続け、リンククリックとストア獲得を記録する。

### 完了の定義

- 主要導線の実機テスト結果が残っている。
- 重大な不具合があれば、再現手順・期待結果・実際の結果をIssueに記録している。
- App StoreとSNSのメッセージが「写真から、次の旅が始まる」に沿っている。
- 認知・インストール・初回利用のどこで止まっているか、少なくとも一つのデータで判断できる。
- 次の開発サイクルで何を優先するか、ユーザーの反応と計測値を根拠に決められる。

## 9. このレビューでまだ断定していないこと

次の項目は、実装コードの個別監査または実機検証を行うまで不具合と断定しない。

- 画像キャッシュ、ページネーション、API再試行の実装が十分か
- いいね・フォロー等が通信失敗時にもサーバー状態と一致するか
- 現在公開中のApp Store掲載内容・検索順位が、文書の記録から変わっていないか
- 本番環境の通知、分析、クラッシュ計測がどこまで稼働しているか
- 実機のメモリ使用量、起動時間、クラッシュ率、各画面の表示速度

これらを「問題あり」と決めつけず、再現可能な検査で判定する。レビューの目的は機能を否定することではなく、Journey Photoの中心価値がユーザーに届き、安心して使い続けられる状態にすることである。
