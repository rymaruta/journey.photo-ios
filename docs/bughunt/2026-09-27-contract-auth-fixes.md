## #1・#10 ログアウトしても、検索・ホーム・地図に前の人あての限定写真が残る

**筋の確認:** `ModerationStore.use` のコメントには「人が変わったときも数を進める」とあるのに、
中身は `bumpIfChanged` だった。そのため、ブロック・通報の集合が変わったときしか `revision` が
進まない。前の人も次の人も0件だと、検索・ホームは読み直さない。
マイページのコメントも「`hidden.use` が数を進める」ことを前提にしていた。

もう1つ穴があった。`hidden.use` は `applyRestrictedFeed()`（限定写真の口の差し替え）より先に
呼ばれていた。集合が変わって数が進む回でも、読み直しが**前の人の口**で走る。ログアウト後は
取れないので、前の人の控えが返っていた。

**直したこと:**
- `ModerationStore.use`: 人が替わったら、集合が同じでも `revision` を進める。
  人の入れ替わりだけを数える `userRevision` を足した
- `JourneyPhotoApp`: `.task(id: auth.userId)` の先頭で口を差し替え、そのあとで `hidden.use` を呼ぶ
- `PublicGalleryService`: 口を差し替えるたびに世代番号を進める。差し替える前に出た要求の答えは、
  控えにも書かず、返しもしない
- 地図: ブロックでは絞るだけなので、`userRevision` が変わったときだけ読み直す。
  ログアウトは見出しのメニュー（シート）から来るので、`.task` が走り直さない
- 地図・検索（f9e9971、レビューの指摘）: 画面に出ていない間に人が替わった回は、
  戻ってきたときに読み直す。札や一覧の元が消えると、開いている詳細がその場で閉じるため
- 地図（0ce69ea・次のコミット）: 戻ってきたときに札を下げると、戻るスワイプを途中でやめた回に
  詳細が閉じる。そこで札は下げず、読み直したピンに差し替える
  - 0ce69ea は `MapPin ==`（座標しか比べない）で「変わったか」を見ていた。そのため一度も
    差し替わらず、前の人あての写真が札に残る回帰を入れていた（レビューで発見）
  - 判断を `PhotoMapViewModel.refreshed` に移し、見つかれば必ず差し替える形にしてテストで固めた
  - 画面に出ている間の入れ替わり（詳細は開いていない）は、読み込みを待たずにすぐ札を下げる
  - 57d1266 のレビューで次を足した
    - 画面に出ている間の読み直しのあとにも差し替える（読み込み中に押した札・開いた一覧）
    - 一覧のシート（`listing`）も同じく差し替える
    - `.task` が取り消された回（戻るスワイプを途中でやめた）と読み込みが落ちた回は、
      札を触らず、「読み直した」の印も進めない（本当に戻ったときに読み直す）
  - 読み込みが落ちた回・読み込みを待っている間は、地図のピンと撮影地の札（`chosenPlace`）が
    前の人の写真のまま残る（担当の範囲を超えるので残した）
  - 一覧のシートの中で詳細を開いている間に人が替わる（期限切れ）と、その写真が次の人の
    一覧に無ければ詳細が閉じる。前の人あての写真を見せ続けない向きに倒した
  - 人の入れ替わりかブロックかは、`onChange` が最後に見た数で見分ける（読み込みが落ちたあとの
    ブロック1回を入れ替わりと取り違えない。d0e6a2d のレビュー）
  - 取り消されたスワイプの最中に読み込みが返ると、ピンが消えて詳細が閉じうる。
    これは読み込みそのもの（`stillShown`）で起きる、前からの動き
- 検索（0ce69ea）: 見ていない間の入れ替わりを `onChange` だけに頼らない。
  2回目以降の出現で数がずれていたら読み直す

**残したこと:**
- 地図の一覧のシート・近くの写真のシートを開いている間の入れ替わりでは、
  シートの中に前の人あての写真が閉じるまで残る（a15fc85 から。シートでは `onDisappear` が来ない）
- 検索で詳細を開いている間のブロック・通報は、今まで通りすぐ読み直す（担当外の既存の動き）
- ホームは `isOnScreen`・`needsReload` の仕組みが元からあるので、手を入れていない

**テスト:** `ViewerChangeTests.swift`（`ModerationUserChangeTests`・`RestrictedLoaderSwapTests`）

**テストで守れていないこと:** 次の2つは SwiftUI の画面の中の話で、この環境の模型では
走らせられない。
- `JourneyPhotoApp` の順番（口の差し替えが先）
- 地図・検索の「画面に出ていない間は後回し」

## #6 期限切れ・圏外のログアウトのあと、前の人あての通知が届き続ける

**筋の確認:**
- `expireSession()` は `push.signingOut()` を通らない
- 人が替わったあとの `use` の中の `DELETE` は効かない。ログアウト後は前の人の ID トークンが無い。
  次の人が入ったあとは、次の人の集合から消すだけになる
- サーバー（`devices.ts`）の `unregisterDevice` は、JWT の `sub` の集合からしか消さない。
  前の持ち主から外せるのは、`registerDevice` の中の `releasePreviousOwner` だけ

**1回目（a15fc85）:** 「外せなかった」の印を、ログアウトの出来事ごとに端末に立てる形にした。
レビューで次の穴が見つかった。
- **起動時の `restore` が期限切れを見つける経路では、`PushCenter` は前の人を一度も知らない。**
  そのため印が立たない。期限切れがいちばん起きやすいのは、使っていない間に切れるこの形
- POST が通って DELETE が落ちると、印が消える。その結果、通知をオフにした人に届く
- 起動し直す形のテストになっていなかったので、修正を守れていなかった

**作り直し（f9e9971）:** 出来事ではなく状態で見る。
- 「この端末をサーバーに最後に登録した人」を端末に残す（`photo-gallery-push-owner`）
  - 登録に成功したら入れる
  - その人で外せたら（ログアウト・受け取らない・外し直し）消す
- `use(userId:)` で持ち主が別の人なら、`POST` で引き取る（前の持ち主から外れる）
- 受け取らない人なら、続けて `DELETE` する
- `DELETE` が落ちても持ち主は残るので、次の `use` でやり直す
- 受け取る人なら `DELETE` しない。外すと、このあと APNs からトークンが返らなかった回に、
  その人の通知まで止まる
- 外している間に「受け取る」を押された回は、外したあとで預け直す

**旧版からの移行（0ce69ea、f9e9971 のレビュー）:** 旧版の端末には持ち主の値が無い。
このままでは、旧版で受け取っていた人が更新後に一度も登録しないまま期限切れになると、
引き取りが走らなかった。そこで「持ち主を一度でも書いたか」
（`photo-gallery-push-owner-known`）を端末に残し、分からない間は次にログインした人で
一度だけ引き取るようにした。更新後に最初にログインした人（本人を含む）で、`POST` が1回流れる。
受け取らない人なら、続けて `DELETE` も1回流れる。

**残る限界:**
- ログアウトしたまま誰もログインしない間は、前の人あての通知が届き続ける。
  端末の側だけでは塞げない（サーバーに「持ち主が抜けた」を伝える口が要る）
- 登録（`POST`）を待っている間にログアウトし、すぐ別の人が入った回は、その起動の間だけ
  前の人あての通知が届きうる。持ち主は正しく残るので、次の起動で引き取る
- サーバーの `releasePreviousOwner`・`forgetTokens` は、DynamoDB で失敗しても 200 を返す。
  そのとき端末の持ち主の値はサーバーとずれ、やり直す手がかりが消える（直すのはサーバー側）
- バックアップから別の機種に復元すると、旧機種のトークンと持ち主が一緒に来る。
  そこで別の人がログインすると旧機種のトークンを引き取り、旧機種を使い続けている人の通知が、
  旧機種の再起動まで止まる（まれ。実機では確かめていない）
- 受け取る人が引き取るときは、手元に残っているトークンで `POST` する。トークンが変わっていたら、
  古いものは APNs の 410 で消えるまで、その人の枠に残る

**テスト:** `PushTests.swift` の `PushReleaseTests`（7本）。元の版（2316e8f）でも、
1回目の版（a15fc85）でも落ちることを確かめた。
受け取る人の経路（`keep`）は、模型の許可が常に「未確認」なので試せていない。

## #21 取り消された通信（`URLError.cancelled`）を「通信できません」と出す

**直したこと:**
- `APIClient` で `.cancelled` を `CancellationError` として投げ直す
- 取り消しを弾いていなかった6画面の読み込みで、`CancellationError` を失敗として出さない。
  6画面はマイページ・アルバム・フォロー一覧・ブロック一覧・人のページ・ストーリーの見た人
- `.unreachable` を見て分岐している所はアプリに無いので、控えに倒す経路は変わらない

**やらなかったこと:**
- ボタン操作（ブロック・作成など）の catch には入れていない。押した操作が途中で取り消される
  経路は見当たらず、スコープを広げないため
- 引き下げ更新の途中で本当に取り消されるか（SwiftUI の挙動）は、実機で確かめていない

**レビューで出て、直さずに残したこと（039c643 のレビュー）:**
- 引き下げ更新の途中で描き直されて取り消される、という根の問題は残る。表に出るのが
  「通信できません」から「何も起きない（古い一覧のまま）」に変わっただけ。根まで直すなら、
  `.refreshable` の中を取り消されない `Task` に逃がす。ただ、取り消しが本当に起きるかを
  実機で確かめておらず、6画面の引き下げの作りを変えることになるので入れていない
- マイページで利用者 ID が nil を挟まずに A から B へ変わると、古い task の取り消しが
  黙って終わり、再試行の帯が出ないことがある（推測。nil を挟まない経路は見つけていない）
- 招待・投稿・通知の設定など、ほかの catch では `CancellationError` が汎用の文言
  （「この招待リンクは使えません」など）になる。どれも画面を離れて task が取り消された
  ときだけで、書き込み系は取り消されない `Task {}` から呼ばれている

**テスト:** `ServerContractTests.swift`（`APIClient` の層だけ。画面の catch は模型では走らない）

## #22 ID トークンの取得失敗が `APIError` に包まれない

**直したこと:** `AuthGateway.idToken` で、次の失敗のうち通信によるものを
`APIError.unreachable` に包む（`AuthGateway.tokenFailure`）。
- 対象の失敗: `fetchAuthSession` の失敗と、トークンの取り出しの失敗
- 通信によるものの見分け: `AuthFailure == .network`、中身が `URLError`、`URLError` そのもの
- それ以外はそのまま投げる。期限切れの判定（`notAuthorized`）は変えていない
- 取り消し（`URLError.cancelled`）は、**呼んだ側が取り消されているときだけ**
  `CancellationError` にする（23bfee8・0d87d3f）
  - 1回目は `APIClient` と食い違い、`unreachable` に包んでいた
  - 2回目は呼び手が生きていても `CancellationError` にしていた。Amplify の中の通信は
    別の URLSession なので、そのままだと画面が黙って抜け、空の画面になる

**確かめられず残したこと:** 指摘書の「もっと重いかもしれない点」は変えていない。
`AuthFailure` は `.sessionExpired` も `.notAuthorized` に数える。圏外で更新に失敗したときに
Amplify 2.x が `.sessionExpired` を返すなら、圏外なだけでログアウトさせることになる。
どちらを返すかは、この環境では確かめられない。
実機での確かめ方（指摘書どおり）: ログインから1時間以上たってから機内モードで起動し、写真を開く。

**テスト:** `ServerContractTests.swift`

## #25 `/user/photos`・`/feed/restricted` を厳しく読み、1行壊れると一覧ごと落ちる

**直したこと:** 公開一覧と同じ `LenientPhotoList` で1行ずつ読む。落とした行の数は記録に残す。
**1行も読めなかったら `APIError.decoding` を投げる**（23bfee8）。1回目はこれが無く、
配列だが全行が崩れた応答が「空の一覧で成功」になっていた。そうなると次のことが起きる。
- マイページが「まだ写真がありません」になる
- 限定写真は、前回の控えを空で上書きする
- 投稿シートは、空のサムネイルを控える

**引き換え:** 1行だけ崩れた写真は、本人のマイページからも見えなくなる（編集・削除もできない）。
崩れた行が本当にあるかは、記録（`print`）でしか分からない。

`LenientPhotoList` は `published: false` の行を落とさない（落とすのは公開一覧の `visible`）。
そのため、自分の写真の下書きは消えない。テストでも確かめた。

**テスト:** `ServerContractTests.swift`

## #14 退会した人のプロフィールが 200 `{userId}` で来る —— 直していない

**筋の確認:** `userProfile.ts` は、プロフィールが無い人と退会した人（墓石）の両方に
200 `{ userId }` を返す。コメントには「墓石は『未設定の人』と同じ見え方にする」とあり、
**わざと区別できない形にしている**。

**直さなかった理由:** アプリで「`{userId}` だけなら見つからない」にすると、プロフィールを
作っていないだけの人（写真はある）まで「退会した可能性があります」と出てしまう。
指摘書も「どちらにするか owner の判断が要る」としている。

**owner に決めてほしいこと:** 退会した人を「見つからない」と出したいなら、サーバーに
退会の印（例: `deleted: true`）を返してもらい、アプリはそれを読む。今のまま
「名前未設定の人」と出すのでよいなら、アプリの 404 の文言は `#` を含む ID 用に残すだけになる。
