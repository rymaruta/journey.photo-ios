# ストーリーの提案5枚 — 実装可否（2026-09-21）

owner から届いたモック5枚を、**サーバーが実際に受ける項目**と突き合わせた。
指示書 5-2 の約束（対応していない機能を実装済みのように見せない）に従い、
**作れるもの／作れないもの／代わりに作れるもの**を先に分ける。

調べた場所: `api-user/src/stories.ts`・`storyReplies.ts`・`storyKeep.ts`、
アプリ側 `Services/StoryService.swift`。

## 1. すぐ作れる（サーバーに既にある）

| モック | 根拠 | 状態 |
|---|---|---|
| **ストーリーの反応 / 見た人の一覧** | `GET /stories/{id}/viewers`（**投稿者本人のみ**）。アプリにも `StoryService.viewers(id:)` が既にある | **画面を作るだけ** |
| 閲覧数 | 同上（`viewers` の数） | 同上 |
| 返信の数・中身 | `GET /stories/{id}/replies`・`replyCount` | 同上 |
| ストーリー作成のテキスト配置 | 2026-09-21 に実装済み（`TextOverlay`・画像に焼き込み） | **済** |
| 場所・BGM の設定 | `location` / `coords` / `song` を受ける | **済**（ステッカーの見た目にはなっていない） |

**ただし「シェア数」は無い。** サーバーが数えていないので、**出さない**
（0 と書くと「誰にも共有されていない」という嘘になる）。

## 2. サーバーに無い（作るならバックエンドの変更が要る）

| モック | 何が無いか | 影響 |
|---|---|---|
| **ハイライト**（丸い表紙・題・ストーリーを選ぶ） | ストーリーをまとめて残す仕組みが無い。`POST /stories` は24時間で消える行を作るだけ | 新しい入れ物（`highlights#<uid>`）とAPI 3本（作成・更新・取得）が要る |
| **公開範囲**（全員 / フォロワーのみ / 親しい友達） | `stories.ts` は公開範囲の項目を受けていない。「親しい友達」の名簿も無い | 保存の項目追加＋読み出し側（`storyFeed`）の絞り込み。**セキュリティに直結**するので、UI だけ先に作ってはいけない |
| **返信を許可（切り替え）** | 1件ごとの可否を持っていない | 項目追加＋`storyReplies` 側の判定 |
| **アーカイブに自動保存** | 自動で残す仕組みが無い（`storyKeep` は**手で1枚ずつ**写真として残す） | 期限切れの処理に手を入れる |
| **位置情報を表示（切り替え）** | 位置は「付ける／付けない」しかない（投稿時に決まる） | 後から隠す項目が要る |

**これらは UI だけ先に作らない。** 押しても効かない切り替えは、
「フォロワーのみにしたつもりが全員に見えている」という**いちばん危ない
勘違い**を生む（指示書 14）。

## 3. 代わりに作れるもの（サーバーにあるが、モックに無い）

**`storyKeep`**——ストーリーの1枚を**ギャラリーの写真として残す**。
Instagram のハイライトが「消えるものを消えないように見せる」だけなのに対し、
こちらは**検索に出る写真そのものに変える**（個別ページ・サイトマップ・
地図・集約ページに載る）。このサイトの優先度（検索流入）にも合う。

ハイライトを作る前に、**この導線を画面に出す**方が先だと考える。

## 4. 進める順（提案）

1. **ストーリーの反応**（見た人・閲覧数・返信）— API があるので今日できる
2. **ストーリー作成をステッカー化**（テキスト／場所／BGM を写真の上に置く）
   — 位置は焼き込みで持てる
3. **「写真として残す」の導線**（`storyKeep`）
4. ハイライト・公開範囲 — **バックエンドの設計から**。別ブランチで
   `api-user` に手を入れる必要があり、owner の許可と反映経路
   （develop → staging → main）が要る
