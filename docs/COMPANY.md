# 体制と提案の流れ（2026-11-07 owner 指示）

owner が**最終決定**を担当し、役割ごとの担当（Claude）が**案出しと提案**をする会社のような体制。

## 役割

| 役割 | 担当の定義 | 主な仕事 |
|---|---|---|
| owner | 人（決定者） | 最終決定。承認・却下・保留 |
| 秘書室（メインの Claude） | この会話 | 依頼の受付、役割への振り分け、提案の取りまとめ、決定後の実行の手配 |
| PM | `.claude/agents/pm.md` | 課題の定義、案出し、優先順位、成功指標 |
| デザイナー | `.claude/agents/designer.md` | 体験・画面・文言・動きの案とモック |
| リサーチ | `.claude/agents/researcher.md` | 競合・市場・利用データ・利用者の声 |
| グロース | `.claude/agents/growth.md` | SEO・導線・登録・継続・計測 |
| エンジニアリングリード | `.claude/agents/eng-lead.md` | 実現性・手間・費用・リスク |
| 実装担当 | `ship-fix` の担当 | 決定後に作る（確かめ役は別の担当） |

## 流れ

1. **案出し**: owner の漠然とした相談 → 秘書室が役割を選び、並列で調べさせる。
2. **提案**: 役割の意見をまとめ、**Artifact の提案書**にして owner に渡す。
3. **決定**: owner が「承認／却下／保留／修正」を決める。札（Issue）に「いいよ」とコメント、または会話で返事。
4. **実行**: 承認されたものだけ、`ship-fix` → Mac → マージ → TestFlight（既存の決まり）。
5. **振り返り**: 出したあとの数字（採用の指標）を見て、次の提案に反映する。

owner の承認が要るもの（CLAUDE.md の決まりのまま）: データベースの変更・新しい GSI・費用が増えるもの・Maintenance の apply=true・方針の転換。
それ以外の細かい仕様は、提案の推奨で進めてよい。

## 提案書（Artifact）の型

先頭から順に、次の見出しを置く。長くしない。

1. **結論と推奨**（1 画面で決められるように。「承認してほしいこと」を 1 行で）
2. **背景と根拠**（数字・出典・日付。確かめていないことは明記）
3. **案**（最低 3 つ。違い・効果・手間を表に。やらない案の理由）
4. **画面・体験**（モックか実画面かを明記）
5. **費用・DB・リスク**（owner の承認が要る点を赤字で）
6. **各役割の意見**（PM・デザイン・リサーチ・グロース・エンジニアリングのうち関わったもの）
7. **決めてほしいこと**（選択肢と推奨）
8. **確かめていないこと**

Artifact の作り方は `artifact-design` の決まりに従う。公開リポジトリなので、本番の鍵・内部の詳しい数字を提案書とこの文書に書かない。
